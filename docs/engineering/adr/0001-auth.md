# ADR 0001: single-owner authentication for Donna (scope of MOS-10 for DON-02)

Status: **approved by the owner on 2026-10-24 for DON-02 only.** It is not a
general authentication design for MoatazOS.

## Decision
- One hosted Supabase project dedicated to Donna. One owner. Public sign-up disabled.
- **Login flow: email and password only**, using accounts the owner creates in the
  dashboard. Magic links, one-time codes, passkeys, OAuth, phone and anonymous
  sign-in are not configured and not supported. Password reset is done in the dashboard.
- **The allowlist is enforced in the database**, not the UI: a trigger on `auth.users`
  rejects any insert or email change to an address not in `donna_allowed_emails`
  (this also blocks anonymous users, who have no email). Row access additionally
  requires the caller's current email to be on the allowlist, so removing an
  address cuts off access even for an existing session.
- **Per-user isolation:** every row carries `owner_id = auth.uid()`; row-level security
  limits reads to the owner; the browser has no table write privilege.
- **Writes only through two database functions** (`donna_upsert_call`,
  `donna_record_event`) that validate type, payload, call reference, time and
  outcome consistency, never trust a client-supplied owner, and distinguish a retry
  (same `event_id`, same content) from a conflicting second outcome. Events and
  calls cannot be updated, deleted or truncated, even by the table owner.
- The browser holds only the public anon key plus the SDK's own auth session in
  browser storage. Domain data is not cached in the browser. The app refuses a
  service-role or secret key in its configuration.

## How the allowlist is proven
Locally: assertions on a throwaway Postgres plus `supabase/tests/hosted_probe.sql`, which also proves it can fail.
Hosted: the same probe in the dedicated synthetic project (fires the trigger directly, independent of the dashboard
sign-up switch), and optionally `npm run test:donna-live-trigger` with sign-up temporarily on. That test needs an
allow-listed control that succeeds under the same conditions, a database-class refusal, no resulting account, and the
cause found in the Postgres logs. Rate limits, network errors, email-delivery errors, bad input and a disabled switch
are INCONCLUSIVE and fail it. A refused sign-up with the dashboard switch OFF is the platform's refusal and is **not**
evidence about the trigger.

## Consequences and limits
- A phone and a laptop are two sessions of the same account.
- Account B (a second allow-listed address) exists only in the test project, to
  prove isolation.
- No MFA yet; the dashboard password and the allowlist are the controls. Passkeys or
  MFA are a later task.
- The browser also validates, but only the database is authoritative. The owner's
  local-date rule uses a fixed UTC+2 demo offset in the browser; the database
  only rejects clearly past or absurd dates until the Africa/Cairo rule lands (DON-04).
- Synthetic data only. Real client data needs G6 and a separate decision on
  repository visibility (OD-2).
