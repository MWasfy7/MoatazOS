2. **Acknowledged, then reload failed.** Reported as `WRITE_CONFIRMED_REFRESH_FAILED` with recovery info; no success notice, form stays open, "Reload from database" or "Save again" recovers without a second outcome.

The clock now refreshes on every reload.
4. **Allowlist evidence.** `supabase/tests/hosted_probe.sql` fires the trigger directly (and checks privileges, RLS, history protections); `npm run test:donna-db` runs it and also proves it can FAIL. `npm run test:donna-live-trigger` exercises the trigger through the Auth API with sign-up temporarily on, and fails if the dashboard switch is still off. ## Repair 2 (independent review of bf476a8)
1. **P1 seeding.** `seedSyntheticCalls` re-checks the identity epoch before EVERY write and stops at once on sign-out, account change or unmount. Regression (hold A's first write, switch to B / sign out / unmount, release): no further write starts.
2. **P2 stale session restoration.** Every auth notification supersedes an in-flight `currentEmail()` lookup (a sequence counter), including a late "signed out" answer; a sign-out notice settles the initial wait. Regression: delayed A lookup after B adopted (A's answer and a null answer) leaves B untouched; a sign-out notice that arrives first beats a late lookup that still says A.
3. **P2 hosted trigger test.** Arbitrary errors no longer count. `decideTriggerEvidence` needs: an allow-listed control that signs up and signs in under the same conditions; a database-class refusal for the unlisted address; proof that no account exists. Rate limit, network, email delivery, bad input, disabled sign-up switch, existing control user: INCONCLUSIVE, and the live test fails on INCONCLUSIVE. Cause is attributed via the Postgres log entry `DONNA_SIGNUP_NOT_ALLOWED`.
   **Finding while testing against the real SDK:** pinned `supabase-js` 2.109.0 wraps every HTTP 5xx as `AuthRetryableFetchError` with the body discarded (message "{}", no code), so a trigger refusal cannot be told from an outage through the SDK. The trigger evidence is therefore read over raw HTTP; a test pins the SDK behaviour. The same finding fixed a shipped bug: the adapter showed a 5xx or a rate limit on sign-in as "wrong password"; it now reports unreachable / rate limited.

## Repair 3 (review of 94c1ea1; required CI `validate` failed on it)
1. **Node 20.** `DonnaTriggerEvidenceSdk.test.ts` failed in CI because `createClient()` builds a realtime client that needs a global `WebSocket`, which Node 20 lacks. The SDK assertion now uses `AuthClient` (the class `createClient` uses for `supabase.auth`; it needs no WebSocket), so it runs on Node 20 and 22. No CI upgrade and no dependency added. **My earlier gates ran on Node 22 only; the gate is now run on Node 20, matching CI.** The live harness (which does use `createClient`) now stops with a clear message on a Node without `WebSocket` and documents Node 22+ (or `NODE_OPTIONS=--experimental-websocket` on Node 20).
2. **Trigger attribution.** The reviewed logic classified a generic 500 / `unexpected_failure` / "Internal server error" as a database rejection and returned PASS. Demonstrated by running the reviewed logic on the reviewer's reproduction: `classify = DATABASE_REJECTION`, `verdict = PASS`. Now: API observations (control succeeds, unlisted refused server-side, no account) and verified log attribution (a log line naming `DONNA_SIGNUP_NOT_ALLOWED` inside the attempt window) are separate; PASS needs both; consistent API observations alone are INCONCLUSIVE; a generic 500 is its own class. The live trigger test is now two-phase (phase 1 cannot pass alone; phase 2 checks the log file). The reviewer's generic-500 case is a regression test, also end to end through raw HTTP against a mock Auth server.
Note: with a verified log line, a generic API message is not disqualifying, because the log line, not the API message, is what attributes the cause.
